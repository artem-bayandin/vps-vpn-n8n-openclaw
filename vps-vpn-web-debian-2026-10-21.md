# VPS Setup Guide (Debian 13): VLESS+Reality VPN + Static Website (Cloudflare)

Debian 13 (trixie) x86-64 edition of `vps-vpn-website-setup-guide-2026-09-17-claude.md`.
Xray-core and Nginx run as native systemd services, with no Docker.

**Decisions locked in:**
- Login: **always `root` with its password** over SSH (`PermitRootLogin yes`,
  `PasswordAuthentication yes`). No SSH key is required, and there is no `deploy` user and no `sudo`.
  The password must be **random, unique and ≥16 characters**, generated by a password manager.
  fail2ban and the non-standard SSH port (2222) are the brute-force mitigations.
- Reality camouflage/target: **www.cloudflare.com** (fallbacks: `www.microsoft.com`, `dl.google.com`).
- Deployment: **native systemd**.
- Website: **static HTML/CSS/JS**, served by Nginx on **8443**. Cloudflare reaches it through an
  **Origin Rule** that rewrites the origin port from 443 to 8443, because Xray owns 443.

**Changes vs. the original guide:**
- Root login with a password. The `deploy` user, `sudo` and SSH keys are removed.
- Debian prerequisites (`curl`, `cron`, …) are installed first.
- SSH uses Debian's `ssh.service` (no socket activation), and the effective config is checked against `sshd_config.d` overrides.
- fail2ban uses the journald (`systemd`) backend, since Debian has no `/var/log/auth.log`.
- An Origin Rule makes Cloudflare connect to 8443, without which the site is unreachable.
- Authenticated Origin Pulls are set up at zone level with **your own CA**, uploaded and enabled via the Cloudflare API.
- Nginx listens on IPv6 as well.
- The Cloudflare IP loop handles the missing trailing newline in Cloudflare's IP lists.
- The UFW-refresh and backup jobs run from root's crontab.
- Backups are encrypted with `age` before going off-box.
- The Xray fallback test uses `--resolve`, since a bare-IP curl always shows a TLS error.
- Section numbering is fixed.

Every command runs as **root**. Replace `<ANGLE_BRACKETS>` with your own values.
Version numbers are fetched live, not hardcoded.

**Reading the expected-output comments:**
- `# expected: ...` describes what a command should print. `# expected: no output` means
  success is silent.
- Commands not marked print nothing you need to check (apt progress, `chmod`, `mkdir`, …).
- Every `tee ... <<'EOF'` command echoes the file content back to the terminal. That's normal.
- Version numbers, keys, IDs and dates in the expected output are placeholders.

## 0. Order of operations

1. Prerequisites + baseline hardening (strong root password, SSH, UFW baseline, fail2ban, unattended upgrades)
2. Xray-core (VLESS + Reality) on port 443
3. Cloudflare (DNS, TLS mode, Origin CA cert, Origin Rule → 8443, zone-level AOP)
4. Nginx origin on port 8443 + static site
5. Finalize UFW (8443 restricted to Cloudflare)
6. Client VPN profile + end-to-end test
7. Encrypted off-box backups
8. Final verification checklist
9. Maintenance cadence

## 1. Prerequisites and baseline hardening

### 1.0 Prerequisites
```
apt update
apt install -y curl cron openssl ca-certificates jq age
systemctl enable --now cron
systemctl is-active cron
# expected: active
```

### 1.1 Strong root password
The provider-issued root password may be short, or it may have been sent by email. Replace it with
a password generated by your password manager: random, unique, ≥16 characters, mixing
a-z, A-Z, digits and symbols. Store it in the password manager first, then set it:
```
passwd
# expected: two "New password:" prompts (input is hidden), then:
#   passwd: password updated successfully
```
Confirm it works from a **new** terminal on your local machine, keeping the current session open:
```
ssh root@<VPS_IP>
# expected: a "root@<VPS_IP>'s password:" prompt; the new password gives a root shell (root@<hostname>:~#)
```
Don't continue until it does. The same password also opens the provider's web console.

### 1.2 System update
```
apt update && apt full-upgrade -y
reboot
# expected: your SSH session drops; reconnect after ~30–60 s
```

### 1.3 SSH hardening (root with password, port 2222)
Check for drop-ins first. sshd uses the **first** value it reads, and
`/etc/ssh/sshd_config.d/*.conf` is included before the main file's settings, so a
provider/cloud-init file such as `50-cloud-init.conf` can silently override you:
```
ls -l /etc/ssh/sshd_config.d/
# expected: "total 0" (empty) or provider files such as 50-cloud-init.conf
```
Put your settings in a drop-in that sorts first:
```
tee /etc/ssh/sshd_config.d/00-hardening.conf <<'EOF'
Port 2222
PermitRootLogin yes
PasswordAuthentication yes
PermitEmptyPasswords no
KbdInteractiveAuthentication no
MaxAuthTries 3
LoginGraceTime 30
EOF
```
`MaxAuthTries 3` and `LoginGraceTime 30` limit each connection to 3 password guesses within 30 s.
fail2ban (§1.5) then bans IPs that keep trying.
Validate the config and print the settings sshd will actually use:
```
sshd -t
# expected: no output

sshd -T | grep -Ei '^(port|passwordauthentication|permitrootlogin|permitemptypasswords|kbdinteractiveauthentication|maxauthtries|logingracetime) '
# expected (any order):
#   port 2222
#   permitrootlogin yes
#   passwordauthentication yes
#   permitemptypasswords no
#   kbdinteractiveauthentication no
#   maxauthtries 3
#   logingracetime 30
```
If any value differs, a file in `sshd_config.d` overrides it; remove the conflicting line from
that file. A common culprit is `PasswordAuthentication no` in `50-cloud-init.conf`.

Debian 13 runs `ssh.service`, not socket activation. Check this:
```
systemctl is-active ssh.socket
# expected: inactive
```
- If it says **inactive** (the normal case):
  ```
  systemctl restart ssh
  # expected: no output
  ss -tlnp | grep sshd
  # expected: LISTEN lines for 0.0.0.0:2222 and [::]:2222 (no :22)
  ```
- Only if it says **active** (some provider images): override the socket's port instead:
  ```
  systemctl edit ssh.socket
  ```
  ```
  [Socket]
  ListenStream=
  ListenStream=2222
  ```
  ```
  systemctl daemon-reload
  systemctl restart ssh.socket
  ss -tlnp | grep 2222
  # expected: LISTEN on *:2222 owned by systemd
  ```

From a **new** terminal (keep the old session open):
```
ssh -p 2222 root@<VPS_IP>
# expected: a "root@<VPS_IP>'s password:" prompt, then a root shell
ssh root@<VPS_IP>
# expected: ssh: connect to host <VPS_IP> port 22: Connection refused
#           (or a timeout once UFW is enabled in §1.4)
```
If your VPS provider has its own network firewall, open 2222/tcp there too.
If you ever get locked out, use the provider's web console with the root password.

### 1.4 UFW baseline (Cloudflare-only 8443 rules come in §5)
```
apt install -y ufw
ufw default deny incoming
# expected: Default incoming policy changed to 'deny'
ufw default allow outgoing
# expected: Default outgoing policy changed to 'allow'
ufw allow 2222/tcp comment 'SSH'
# expected: Rules updated / Rules updated (v6)
ufw allow 443/tcp comment 'Xray VLESS+Reality'
# expected: Rules updated / Rules updated (v6)
ufw enable
# expected: a "Command may disrupt existing ssh connections" prompt; answer y, then:
#           Firewall is active and enabled on system startup
ufw status verbose
# expected:
#   Status: active
#   Default: deny (incoming), allow (outgoing), disabled (routed)
#   2222/tcp        ALLOW IN    Anywhere      # SSH
#   443/tcp         ALLOW IN    Anywhere      # Xray VLESS+Reality
#   2222/tcp (v6)   ALLOW IN    Anywhere (v6) # SSH
#   443/tcp (v6)    ALLOW IN    Anywhere (v6) # Xray VLESS+Reality
```

### 1.5 fail2ban for SSH (journald backend)
Debian has no `/var/log/auth.log` by default, so fail2ban reads the systemd journal:
```
apt install -y fail2ban python3-systemd
tee /etc/fail2ban/jail.local <<'EOF'
[sshd]
enabled  = true
port     = 2222
backend  = systemd
maxretry = 4
findtime = 10m
bantime  = 1h
EOF
systemctl enable fail2ban
systemctl restart fail2ban
systemctl is-active fail2ban
# expected: active
fail2ban-client status sshd
# expected:
#   Status for the jail: sshd
#   |- Filter
#   |  |- Currently failed: 0
#   |  |- Total failed:     0
#   |  `- Journal matches:  _SYSTEMD_UNIT=sshd.service + _COMM=sshd ...
#   `- Actions
#      |- Currently banned: 0
#      |- Total banned:     0
#      `- Banned IP list:
```
To check that failures are counted, try a wrong password once from another IP:
`ssh -p 2222 root@<VPS_IP>`. Afterwards `Total failed` should be ≥ 1. Don't exceed 3 wrong
attempts from your own IP, or you'll ban yourself for an hour.

If you ban yourself, the SSH connection times out instead of being refused. Unban from the
provider console:
```
fail2ban-client set sshd unbanip <YOUR_IP>
# expected: 1
```

### 1.6 Unattended security upgrades
```
apt install -y unattended-upgrades apt-listchanges
dpkg-reconfigure -plow unattended-upgrades
# expected: a dialog "Automatically download and install stable updates?" → choose Yes
cat /etc/apt/apt.conf.d/20auto-upgrades
# expected:
#   APT::Periodic::Update-Package-Lists "1";
#   APT::Periodic::Unattended-Upgrade "1";
```

## 2. Xray-core (VLESS + Reality) on port 443

### 2.1 Install (official installer, native systemd unit)
```
curl -s https://api.github.com/repos/XTLS/Xray-core/releases/latest | grep '"tag_name"'
# expected: "tag_name": "vX.Y.Z",
bash -c "$(curl -L https://github.com/XTLS/Xray-install/raw/main/install-release.sh)" @ install
# expected (near the end): info: Xray vX.Y.Z is installed.
xray version
# expected (first line): Xray X.Y.Z (Xray, Penetrates Everything.) ... linux/amd64
```
The installed version should match the tag. Read the release notes at
`github.com/XTLS/Xray-core/releases` before each upgrade, because REALITY config fields change.
The installed unit runs as `nobody` with `CAP_NET_BIND_SERVICE`, so binding 443 works.

### 2.2 Generate credentials
```
xray x25519
# expected:
#   PrivateKey: <43-char base64url>   → server config "privateKey"
#   Password: <43-char base64url>     → client "pbk" (public key)
#   Hash32: <...>                     → not needed
xray uuid
# expected: one UUID, e.g. 1b2c3d4e-5f60-4a7b-8c9d-0e1f2a3b4c5d
openssl rand -hex 8
# expected: 16 hex chars, e.g. a1b2c3d4e5f60718
```
Older Xray builds print `Private key:` / `Public key:` instead.

### 2.3 Validate the Reality target
```
curl -so /dev/null -w '%{http_version} %{http_code}\n' --http2 -A "Mozilla/5.0" https://www.cloudflare.com
# expected: 2 200
openssl s_client -connect www.cloudflare.com:443 -tls1_3 -servername www.cloudflare.com </dev/null 2>/dev/null | grep -E 'Protocol|Cipher'
# expected: line(s) containing TLSv1.3 and a TLS_AES_* or TLS_CHACHA20_* cipher, e.g.
#   New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
```
If either check fails, switch to `www.microsoft.com` or `dl.google.com`.

### 2.4 Server config
| Placeholder | Command | Which part of the output |
|---|---|---|
| `<CLIENT_UUID>` | `xray uuid` | the whole line, e.g. `1b2c3d4e-5f60-4a7b-8c9d-0e1f2a3b4c5d` |
| `<PRIVATE_KEY>` | `xray x25519` | the **`PrivateKey:`** line only, not `Password:` |
| `<SHORT_ID>` | `openssl rand -hex 8` | the whole line, e.g. `a1b2c3d4e5f60718` |

The short ID isn't produced by Xray. It's any hex string you choose: even length, at most 16 characters. `openssl rand -hex 8` just generates a random one for you.

Save the `Password:` line from `xray x25519` as well. Together with the UUID and short ID, it goes into the client link in §6:

```
vless://<CLIENT_UUID>@<VPS_IP>:443?...&pbk=<Password value>&...&sid=<SHORT_ID>#vps-vpn
```

The UUID and short ID must be identical on the server and in the client link. The client gets the public key (`Password`), never the private key.

```
tee /usr/local/etc/xray/config.json <<'EOF'
{
  "log": {
    "loglevel": "warning",
    "access": "/var/log/xray/access.log",
    "error": "/var/log/xray/error.log"
  },
  "inbounds": [
    {
      "listen": "0.0.0.0",
      "port": 443,
      "protocol": "vless",
      "settings": {
        "clients": [
          { "id": "<CLIENT_UUID>", "flow": "xtls-rprx-vision", "email": "client1" }
        ],
        "decryption": "none"
      },
      "streamSettings": {
        "network": "raw",
        "security": "reality",
        "realitySettings": {
          "show": false,
          "target": "www.cloudflare.com:443",
          "xver": 0,
          "serverNames": ["www.cloudflare.com"],
          "privateKey": "<PRIVATE_KEY>",
          "shortIds": ["<SHORT_ID>"]
        }
      },
      "sniffing": { "enabled": true, "destOverride": ["http", "tls"] }
    }
  ],
  "outbounds": [
    { "protocol": "freedom", "tag": "direct" },
    { "protocol": "blackhole", "tag": "block" }
  ]
}
EOF
chmod 644 /usr/local/etc/xray/config.json
```
`"listen": "0.0.0.0"` is IPv4 only. If clients should connect over IPv6, change it to `"::"`.
Requests without valid VLESS credentials are transparently proxied to www.cloudflare.com.

### 2.5 Start and verify
```
xray run -test -config /usr/local/etc/xray/config.json
# expected (last line): Configuration OK.
systemctl enable --now xray
systemctl restart xray
systemctl status xray --no-pager
# expected: Active: active (running). If not, read the $2.5.1
ss -tlnp | grep ':443'
# expected: LISTEN ... 0.0.0.0:443 ... users:(("xray",pid=...,fd=...))
```
To check the fallback from **another machine**, send the real SNI to your IP. A bare
`curl https://<VPS_IP>` always fails, because it sends no SNI and the certificate doesn't match an IP:
```
curl -sv --resolve www.cloudflare.com:443:<VPS_IP> https://www.cloudflare.com -o /dev/null 2>&1 | grep -E 'subject:|HTTP/'
# expected:
#   *  subject: CN=...cloudflare.com          (Cloudflare's real certificate)
#   < HTTP/2 200
```

### 2.5.1 Help
Might fail with error: "Failed to start: main: failed to create server > app/log: failed to initialize access logger > open /var/log/xray/access.log: permission denied". Most likely, not an expected user owns some files.

Find out.

```
ls -l /var/log/xray/
# expected now: access.log / error.log owned by root root  ← the problem

systemctl cat xray | grep -E '^User='
# expected: User=xray or User=nobody
```

Fix.

```
id xray
# expected: uid=... (xray) gid=... (xray or nogroup) groups=...

chown -R xray: /var/log/xray
chmod 755 /var/log/xray
chmod 644 /var/log/xray/*.log

ls -l /var/log/xray/
# expected: -rw-r--r-- 1 xray <group from id> 0 ... access.log
#           -rw-r--r-- 1 xray <group from id> 0 ... error.log

systemctl restart xray
systemctl status xray --no-pager
# expected: Active: active (running)
ss -tlnp | grep ':443'
# expected: LISTEN ... 0.0.0.0:443 ... users:(("xray",...))
```

### 2.6 Key hygiene
- Store the private key, public key (Password), UUID and short ID in a password manager.
- Rotate them every 3–6 months: regenerate via §2.2, update the config, run
  `systemctl restart xray`, and reissue client links.

## 3. Cloudflare configuration

All steps are in the Cloudflare dashboard at https://dash.cloudflare.com unless a command block says
otherwise. Cloudflare occasionally moves menu items; if a label doesn't match, use the dashboard's
search box at the top.

### 3.0 Add the domain to Cloudflare (skip if the domain already shows **Active**)
1. **Add a domain** (or **Onboard a domain**) → enter `<yourdomain.com>` → choose the **Free** plan →
   let Cloudflare scan your existing records.
2. Cloudflare shows two nameservers, e.g. `ada.ns.cloudflare.com` and `bob.ns.cloudflare.com`.
3. At your **domain registrar**, replace the current nameservers with those two.
4. Wait until the domain's **Overview** page says **Active** (minutes to a few hours; Cloudflare
   emails you when it's done).

Check from any machine:
```
dig +short NS <yourdomain.com>
# expected: the two *.ns.cloudflare.com nameservers
```

### 3.1 DNS records
Select your domain → left sidebar **DNS → Records**.

1. **Delete** any existing `A`, `AAAA` or `CNAME` records for `@` or `www` that point elsewhere
   (e.g. the registrar's parking page).
2. Click **Add record** and create:

   | Type | Name | IPv4 address | Proxy status | TTL |
   |---|---|---|---|---|
   | A | `@` (the apex, `<yourdomain.com>`) | `<VPS_IP>` | **Proxied** (orange cloud) | Auto |
   | A | `www` | `<VPS_IP>` | **Proxied** (orange cloud) | Auto |

3. If the VPS has a public IPv6 address, add two `AAAA` records (`@` and `www`) the same way:
   ```
   ip -6 addr show scope global
   # expected: an "inet6 <IPv6>/<prefix> scope global" line if the VPS has IPv6; no output if it doesn't
   ```
4. Click **Save** after each record.

The cloud must be **orange**. A grey cloud ("DNS only") exposes the VPS IP and bypasses everything
below.

Do **not** create any record for the VPN. Clients connect to the raw `<VPS_IP>:443`.

Check from any machine:
```
dig +short <yourdomain.com>
dig +short www.<yourdomain.com>
# expected: Cloudflare IPs (e.g. 104.21.x.x / 172.67.x.x), NOT <VPS_IP>
```

### 3.2 TLS mode
**SSL/TLS → Overview**:
1. Click **Configure** → choose **Custom SSL/TLS**. The default "Automatic SSL/TLS" may pick a weaker
   mode.
2. Select **Full (strict)** → **Save**. Never use Flexible.

Until Nginx serves the origin certificate (§4), the site shows error **521** or **526**. That's
expected at this point.

Recommended, under **SSL/TLS → Edge Certificates**:
- **Always Use HTTPS**: On
- **Minimum TLS Version**: TLS 1.2
- **TLS 1.3**: On

### 3.3 Origin CA certificate (what Nginx presents)
**SSL/TLS → Origin Server → Create Certificate**:
1. **Generate private key and CSR with Cloudflare**.
2. **Private key type**: RSA (2048) or ECC. Either works.
3. **Hostnames**: `<yourdomain.com>`, `*.<yourdomain.com>` (pre-filled).
4. **Certificate Validity**: 15 years → **Create**.
5. **Key format**: **PEM**.
6. Copy the **Origin Certificate** box into one local text file and the **Private Key** box into
   another. The key is shown only once.

These go into `/etc/nginx/ssl/origin.pem` and `/etc/nginx/ssl/origin.key` in §4.2. In `nano`, paste
with right-click or Ctrl+Shift+V, then save with Ctrl+O, Enter, Ctrl+X.

### 3.4 Origin Rule: send origin traffic to 8443 (required)
Cloudflare connects to the origin on the port the visitor used (443), and on this host 443 belongs
to Xray. Rewrite the origin port:

**Rules → Overview → Create rule → Origin Rule**:
1. **Rule name**: `website to 8443`.
2. **If incoming requests match…** → **Custom filter expression**:
   - Field **Hostname**, operator **is in**, value `<yourdomain.com>`, press Enter, then add
     `www.<yourdomain.com>`.
   - Or click **Edit expression** and paste:
     ```
     (http.host in {"<yourdomain.com>" "www.<yourdomain.com>"})
     ```
3. **Then…** → **Destination Port** → **Rewrite to…** → `8443`.
4. Leave Host Header, SNI and DNS Record unchanged.
5. **Deploy**.

Visitors still use `https://<yourdomain.com>` on 443. Only the Cloudflare → origin leg uses 8443.

After §4 and §5 are done, check from any machine:
```
curl -sI https://<yourdomain.com> | grep -iE '^(HTTP|server)'
# expected:
#   HTTP/2 200
#   server: cloudflare
```
If it fails, the Cloudflare error code tells you why:

| Code | Meaning | Check |
|---|---|---|
| 521 | Origin refused the connection | Nginx isn't listening on 8443, or the Origin Rule is missing, so traffic hits Xray on 443 |
| 522 | Connection timed out | UFW is blocking Cloudflare on 8443 (§5) |
| 525 / 526 | TLS handshake failed / certificate invalid | `origin.pem` / `origin.key` are wrong or mismatched |
| 400 "No required SSL certificate was sent" | Nginx requires a client certificate that Cloudflare isn't sending | AOP isn't enabled or active (§3.5) |

### 3.5 Zone-level Authenticated Origin Pulls (own CA, via API)
The dashboard toggle alone enables only the **global** shared Cloudflare certificate, which
proves a request came from Cloudflare but not from *your* zone. Zone-level AOP with your own
client certificate is uploaded and enabled through the API.

**Where to run the commands:** on the VPS (`openssl`, `curl` and `jq` were installed in §1.0) or on
any machine that has them. If you run them on the VPS, copy the CA certificate into place once
`/etc/nginx/ssl` exists (§4.2): `cp ~/aop/aop-ca.pem /etc/nginx/ssl/aop-ca.pem`. Then move
`aop-ca.key` off the server.

**a) Create your CA and client certificate:**
```
mkdir -p ~/aop && cd ~/aop && umask 077
openssl genrsa -out aop-ca.key 4096
# expected: no output
openssl req -x509 -new -key aop-ca.key -sha256 -days 3650 -subj "/CN=<yourdomain.com> AOP CA" -out aop-ca.pem
# expected: no output
openssl genrsa -out aop-client.key 2048
# expected: no output
openssl req -new -key aop-client.key -subj "/CN=cloudflare-aop-<yourdomain.com>" -out aop-client.csr
# expected: no output
printf "basicConstraints=CA:FALSE\nkeyUsage=digitalSignature,keyEncipherment\nextendedKeyUsage=clientAuth\n" > client.ext
openssl x509 -req -in aop-client.csr -CA aop-ca.pem -CAkey aop-ca.key -CAcreateserial \
  -days 825 -sha256 -extfile client.ext -out aop-client.pem
# expected:
#   Certificate request self-signature ok
#   subject=CN=cloudflare-aop-<yourdomain.com>
openssl verify -CAfile aop-ca.pem aop-client.pem
# expected: aop-client.pem: OK
```
Only `aop-ca.pem` goes to Nginx. Keep `aop-ca.key` offline, in your password manager or an
encrypted vault.

**b) Zone ID and API token:**
- **Zone ID:** your domain's **Overview** page → right-hand column, section **API** → click to copy
  **Zone ID**.
- **API token:**
  1. Person icon (top right) → **My Profile → API Tokens** → **Create Token**.
  2. **Create Custom Token** → **Get started**.
  3. **Token name**: `aop-upload`.
  4. **Permissions**: `Zone` · `SSL and Certificates` · `Edit`.
  5. **Zone Resources**: `Include` · `Specific zone` · `<yourdomain.com>`.
  6. **Continue to summary** → **Create Token** → copy the token (shown only once).

**c) Upload the client certificate and enable it:**
```
export CF_API_TOKEN=<TOKEN>
export ZONE_ID=<ZONE_ID>

curl -s "https://api.cloudflare.com/client/v4/user/tokens/verify" \
  -H "Authorization: Bearer $CF_API_TOKEN" | jq '.success, .result.status'
# expected:
#   true
#   "active"

jq -n --rawfile c aop-client.pem --rawfile k aop-client.key \
  '{certificate:$c, private_key:$k}' > upload.json

curl -s -X POST "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/origin_tls_client_auth" \
  -H "Authorization: Bearer $CF_API_TOKEN" -H "Content-Type: application/json" \
  --data @upload.json | jq '.success, .result.id, .result.status'
# expected:
#   true
#   "<certificate-id>"
#   "initializing" or "pending_deployment"
# (false = check the token permission and Zone ID; run without "| jq ..." to see .errors)

# Repeat every minute or so until status = "active":
curl -s "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/origin_tls_client_auth" \
  -H "Authorization: Bearer $CF_API_TOKEN" | jq '.result[] | {id, status, expires_on}'
# expected: { "id": "<certificate-id>", "status": "active", "expires_on": "<date ~825 days ahead>" }

curl -s -X PUT "https://api.cloudflare.com/client/v4/zones/$ZONE_ID/origin_tls_client_auth/settings" \
  -H "Authorization: Bearer $CF_API_TOKEN" -H "Content-Type: application/json" \
  --data '{"enabled":true}' | jq '.success, .result'
# expected:
#   true
#   { "enabled": true }

shred -u upload.json
# expected: no output
```
Check in the dashboard: **SSL/TLS → Origin Server** → **Authenticated Origin Pulls** shows **On**.

Enable AOP in Cloudflare **before** Nginx turns on `ssl_verify_client on`. Otherwise every
request returns 400 ("No required SSL certificate was sent").

When you're done, delete the token (**My Profile → API Tokens** → `aop-upload` → **Delete**), and
create a new one when you renew the client certificate.

## 4. Nginx (native) origin on 8443 + static site

### 4.1 Install
```
apt install -y nginx
systemctl disable --now apache2 2>/dev/null || true
```

## 5. Finalize UFW (8443 → Cloudflare only)

Use one script for both the initial run and the monthly cron.
`|| [ -n "$ip" ]` keeps the last line, which Cloudflare's lists end without a newline.
```
tee /usr/local/sbin/cf-ufw-refresh.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
TMP=$(mktemp -d)
trap 'rm -rf "$TMP"' EXIT
curl -fsS https://www.cloudflare.com/ips-v4 -o "$TMP/v4"
curl -fsS https://www.cloudflare.com/ips-v6 -o "$TMP/v6"
for f in "$TMP/v4" "$TMP/v6"; do
  while read -r ip || [ -n "$ip" ]; do
    [ -z "$ip" ] && continue
    ufw allow from "$ip" to any port 8443 proto tcp comment 'Cloudflare' >/dev/null
  done < "$f"
done
EOF
chmod 700 /usr/local/sbin/cf-ufw-refresh.sh
/usr/local/sbin/cf-ufw-refresh.sh
# expected: no output (any output = error, e.g. curl couldn't download a list)
ufw status numbered
# expected:
#   [ 1] 2222/tcp                   ALLOW IN    Anywhere          # SSH
#   [ 2] 443/tcp                    ALLOW IN    Anywhere          # Xray VLESS+Reality
#   [ 3] 8443/tcp                   ALLOW IN    173.245.48.0/20   # Cloudflare
#   ... one 8443 line per Cloudflare CIDR, then the (v6) equivalents
#   No other ports, and no 8443 rule from "Anywhere".
ufw status | grep -c Cloudflare
# expected: the same number as the Cloudflare CIDR count, which this command shows:
{ curl -s https://www.cloudflare.com/ips-v4; echo; curl -s https://www.cloudflare.com/ips-v6; echo; } | grep -c /
```
Monthly refresh in root's crontab:
```
(crontab -l 2>/dev/null; echo "0 4 1 * * /usr/local/sbin/cf-ufw-refresh.sh") | crontab -
crontab -l
# expected: includes  0 4 1 * * /usr/local/sbin/cf-ufw-refresh.sh
```
The script only adds rules. If Cloudflare ever retires a range, delete its rule manually
(`ufw status numbered`, then `ufw delete <N>`).

### 6.1. Possible issue

- site shows 403 Forbidden, with nginx label at the bottom

First find out who is returning the 403: Cloudflare or your Nginx. The page itself tells you:

| What the page looks like | Who sent it |
|---|---|
| Plain white page saying **403 Forbidden**, with **nginx** at the bottom | Your Nginx (most likely) |
| Cloudflare-branded page ("Sorry, you have been blocked", "Error 1xxx", with a **Ray ID**) | Cloudflare |

**1. Check the response headers** from your computer, with the VPN off:
```
curl -sI https://shept.xyz | grep -iE '^(HTTP|server|cf-ray)'
# Nginx 403:      HTTP/2 403, server: cloudflare, cf-ray: ...
# Cloudflare 403: HTTP/2 403, server: cloudflare, cf-ray: ...  (same headers, so also check the body)
curl -s https://shept.xyz | head -20
# Nginx:      <center>nginx</center>
# Cloudflare: "cloudflare" branding, "error code", "Ray ID"
```

**2. Check whether the request reached Nginx** (on the VPS):
```
tail -n 5 /var/log/nginx/access.log
# expected if Nginx answered: a line with "GET / HTTP/2.0" 403 from a Cloudflare IP
tail -n 5 /var/log/nginx/error.log
# common causes:
#   "directory index of "/var/www/site/" is forbidden" → no index.html
#   "open() "/var/www/site/index.html" failed (13: Permission denied)" → file permissions
```
No new line in `access.log` means the request never reached Nginx. In that case the problem is in Cloudflare (step 4).

**3. If Nginx returned the 403**, fix the site files:
```
ls -la /var/www/site/
# expected: index.html is present (your build output must include index.html at the top level)

chown -R root:root /var/www/site
find /var/www/site -type d -exec chmod 755 {} +
find /var/www/site -type f -exec chmod 644 {} +
namei -l /var/www/site/index.html
# expected: every directory on the path is drwxr-xr-x and the file is -rw-r--r--
```
Nginx's worker runs as `www-data`, so it needs read access to the files and execute access to every directory on the path. Files copied in with `scp` or `rsync -a` often arrive as `-rw-------`, which `www-data` can't read.

**at this point it started working properly**

To test Nginx directly, bypassing Cloudflare, use the client certificate from §3.5a if it's still on the VPS:
```
curl -sk --resolve <yourdomain.com>:8443:127.0.0.1 \
  --cert ~/aop/aop-client.pem --key ~/aop/aop-client.key \
  https://<yourdomain.com>:8443/
# expected: <!doctype html><html><body><h1>It works.</h1></body></html>
```

**4. If Cloudflare returned the 403** (branded page, nothing in the Nginx access log):
- **Security → Events:** look for your request. Cloudflare shows which rule blocked it, such as a WAF custom rule, Bot Fight Mode or a country block. Disable or adjust that rule.
- **Security → Settings:** check that **Security Level** isn't set to "I'm Under Attack", and turn off **Bot Fight Mode** while you test.
- **Rules → Overview:** confirm the Origin Rule from §3.4 is **deployed** and its hostnames match your domain exactly.

## 7. Encrypted off-box backups

The backup contains the Reality private key and the origin key, so encrypt it with `age`.

On your **local machine** (not the VPS):
```
age-keygen -o vps-backup.agekey     # keep this file safe; it decrypts the backups
# expected: Public key: age1<58 more chars>
```
Copy the `age1...` public key it prints. Then on the VPS:
```
mkdir -p /opt/backups
chmod 700 /opt/backups
echo "age1<YOUR_PUBLIC_KEY>" > /opt/backups/age-recipient.txt

tee /opt/backups/backup.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
umask 077
STAMP=$(date +%F)
WORK=$(mktemp -d)
trap 'rm -rf "$WORK"' EXIT

cp -r /usr/local/etc/xray        "$WORK/xray-config"
cp -r /etc/nginx/sites-available "$WORK/nginx-sites"
cp -r /etc/nginx/ssl             "$WORK/nginx-ssl"
cp -r /etc/ssh/sshd_config.d     "$WORK/sshd_config.d"
cp -r /var/www/site              "$WORK/site"

tar czf - -C "$WORK" . | age -R /opt/backups/age-recipient.txt \
  -o "/opt/backups/vps-backup-$STAMP.tar.gz.age"
EOF
chmod 700 /opt/backups/backup.sh
/opt/backups/backup.sh
# expected: no output
ls -lh /opt/backups/
# expected: age-recipient.txt, backup.sh, vps-backup-YYYY-MM-DD.tar.gz.age (a few KB)
head -c 21 /opt/backups/vps-backup-$(date +%F).tar.gz.age; echo
# expected: age-encryption.org/v1
```
Schedule it in root's crontab:
```
(crontab -l 2>/dev/null; echo "0 3 * * * /opt/backups/backup.sh") | crontab -
```
Off-box sync: install rclone and configure a remote:
```
apt install -y rclone
rclone config
# expected: an interactive wizard; create a remote named "remote"
rclone lsd remote:
# expected: a list of top-level folders/buckets (no error)
(crontab -l 2>/dev/null; echo "30 3 * * * rclone copy /opt/backups/ remote:vps-backups/ --include 'vps-backup-*.tar.gz.age'") | crontab -
crontab -l
# expected: three lines – cf-ufw-refresh.sh (0 4 1 * *), backup.sh (0 3 * * *), rclone copy (30 3 * * *)
```
To restore (on your local machine):
```
age -d -i vps-backup.agekey vps-backup-<DATE>.tar.gz.age | tar xzf -
# expected: no output; folders xray-config/, nginx-sites/, nginx-ssl/, sshd_config.d/, site/ appear
```

## 8. Final verification checklist

- [x] `ssh -p 2222 root@<VPS_IP>` asks for the password and logs in with it.

- [x] `ufw status` shows only 2222/tcp, 443/tcp and 8443/tcp from Cloudflare CIDRs.

- [x] `curl -sv --resolve www.cloudflare.com:443:<VPS_IP> https://www.cloudflare.com` returns Cloudflare's certificate and `HTTP/2 200`.
- [x] The VPN client connects via the §6 link, and the egress IP is the VPS.
- [x] `https://<yourdomain.com>` loads the site through Cloudflare (Origin Rule → 8443).
- [ ] Zone-level AOP status is `active` (§3.5), and the site still loads with `ssl_verify_client on`.
- [x] `crontab -l` lists the UFW refresh, backup and rclone jobs.
- [ ] `/opt/backups/backup.sh` produces a `.tar.gz.age`, and the off-box copy lands; a test restore decrypts.

## 9. Maintenance cadence

- **Monthly:** run `apt update && apt full-upgrade -y`, compare the Xray release tag with
  `xray version` (they should be equal), and confirm the UFW refresh cron ran
  (`ufw status | grep -c Cloudflare` should equal the CIDR count from §5).
- **Quarterly:** rotate the Reality keys, UUIDs and short IDs (§2.6), and test a backup restore.
- **Before ~2 years (825 days):** reissue the AOP client certificate (§3.5a), upload it,
  confirm it's active, then delete the old one via the API.
- **As needed:** if `www.cloudflare.com` fails the §2.3 checks, switch to `www.microsoft.com`
  or `dl.google.com` (update `target` and `serverNames`) and reissue client links.
